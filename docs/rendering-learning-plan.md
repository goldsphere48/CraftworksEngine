# Глобальный план обучения рендерингу

## Цель

Научиться осознанно проектировать и реализовывать рендерер: понимать путь данных
от CPU до изображения, устройство GPU-ресурсов, формирование кадра, архитектурные
границы и причины появления таких сущностей, как `Mesh`, `Pipeline`, `Material`,
`RenderObject` и `RenderPass`.

Линейная алгебра не входит в основной план. К ней следует возвращаться точечно,
если конкретная тема обнаружит пробел.

Основной принцип:

> На каждом этапе сначала изучается модель, затем она наблюдается в работе,
> объясняется своими словами и только после этого проектируется собственное
> решение.

Архитектура не должна строиться заранее как набор «правильных» сущностей. Она
должна становиться следствием понятых проблем и требований.

## 0. Способ обучения

Прогресс измеряется не количеством написанного кода, а способностью объяснять,
предсказывать, диагностировать и сравнивать решения.

Для каждой темы используется один цикл:

1. Сформулировать вопрос.
2. Изучить теоретическую модель.
3. Предсказать поведение системы.
4. Провести небольшой изолированный эксперимент.
5. Наблюдать результат через логи, отладчик или GPU debugger.
6. Объяснить результат без подсказок.
7. Сравнить несколько вариантов решения.
8. Записать выводы.
9. Через несколько дней воспроизвести понимание по памяти.

Результатом занятия считается способность ответить:

- почему это работает;
- какие данные участвуют;
- где они находятся;
- кто ими владеет;
- когда они изменяются;
- что произойдёт при изменении условий;
- какие альтернативные решения возможны.

## 1. Ментальная модель GPU

### Цель

Перестать воспринимать графический API как набор магических вызовов.

### Область изучения

- разделение CPU и GPU;
- устройство кадра;
- graphics pipeline;
- draw call;
- vertex processing;
- сборка примитивов;
- clipping;
- rasterization;
- interpolation;
- fragment processing;
- depth и stencil tests;
- blending;
- framebuffer;
- представление данных на GPU;
- асинхронность CPU и GPU.

Главный вопрос этапа:

> Что физически и логически происходит с данными от момента подготовки на CPU
> до появления изображения?

Практика должна быть исследовательской: изменить одно условие, заранее
предсказать результат, затем объяснить наблюдаемое.

### Критерий завершения

Можно нарисовать схему одного кадра и объяснить роль каждой стадии, не ссылаясь
на архитектуру Clearwater или особенности конкретного API.

## 2. Графический API как интерфейс к GPU

### Цель

Понять, какие обязанности графический API берёт на себя и как выражает общие
графические понятия.

### Область изучения

- graphics context и device;
- GPU resources;
- buffers;
- textures и samplers;
- shaders и shader programs;
- vertex layouts;
- render state;
- render targets;
- resource binding;
- draw commands;
- presentation и swap chain;
- ошибки API и validation;
- implicit state и explicit state.

Нужно постоянно разделять:

```text
графическое понятие
!=
способ его выражения в OpenGL
!=
способ его выражения в DirectX 12
```

Например, vertex buffer — общее понятие, а `GLuint` — только его представление
в OpenGL.

OpenGL на этом этапе используется как средство наблюдения: он позволяет увидеть
основные операции без большого количества инфраструктуры.

### Критерий завершения

Для каждого значимого вызова API понятно, какой ресурс или состояние GPU он
создаёт, изменяет либо использует.

## 3. Ресурсы, память и время жизни

### Цель

Научиться видеть рендерер как систему владения ресурсами.

### Область изучения

- CPU memory и GPU memory;
- создание, загрузка, использование и уничтожение ресурсов;
- immutable и dynamic resources;
- обновление данных;
- staging и upload memory;
- handles;
- ownership;
- lifetime;
- кеширование;
- reference counting;
- deferred destruction;
- синхронизация использования и уничтожения;
- стоимость аллокаций;
- утечки и use-after-free.

Для каждой сущности следует составлять таблицу:

| Вопрос | Ответ |
|---|---|
| Какие данные она хранит? | |
| Где находятся эти данные? | |
| Кто создаёт ресурс? | |
| Кто является владельцем? | |
| Кто может только ссылаться? | |
| Когда ресурс уничтожается? | |
| Может ли GPU ещё использовать его? | |

### Критерий завершения

Можно спроектировать время жизни ресурса и заранее назвать основные ошибки
владения и синхронизации.

## 4. Словарь архитектуры рендерера

### Цель

Понять происхождение архитектурных сущностей вместо заучивания их названий.

Изучать нужно проблему, из которой появляется каждая сущность:

- `Buffer` — память GPU определённого назначения;
- `Texture` — структурированное изображение или массив данных;
- `Mesh` — представление геометрии;
- `Shader` — программируемая стадия pipeline;
- `Pipeline` — алгоритм и состояние отрисовки;
- `Material` — конкретная конфигурация поверхности;
- `RenderObject` — запрос нарисовать сущность в конкретном состоянии;
- `Camera` — параметры наблюдения сцены;
- `RenderList` — описание работы на кадр;
- `RenderPass` — логическая стадия построения изображения;
- `RenderTarget` — место назначения результата;
- `GraphicsDevice` — API управления графическими ресурсами и командами;
- `Asset` — долговременное содержимое, полученное из внешнего источника.

Для каждой сущности нужно выяснять:

1. Какую проблему она решает?
2. Какие данные обязаны находиться вместе?
3. Что она не должна знать?
4. Где проходит граница владения?
5. Может ли она существовать независимо от конкретного API?
6. Что потеряется, если её удалить?

### Критерий завершения

Необходимость сущности можно вывести из требований, не ссылаясь на то, что такое
название встречается в другом движке.

## 5. Слои и направление зависимостей

### Цель

Научиться разделять ответственность и проводить границы между подсистемами.

Базовая модель зависимостей:

```text
game/scene
    |
    v
renderer
    |
    v
graphics abstraction
    |
    v
graphics backend
    |
    v
API и GPU
```

Путь внешних данных рассматривается отдельно:

```text
files
    |
    v
asset system
    |
    v
runtime resources
```

### Область изучения

- публичный и внутренний API;
- однонаправленные зависимости;
- границы модулей;
- backend-neutral descriptions;
- data-oriented interfaces;
- handles и прямые указатели;
- context и state structures;
- function tables;
- цена абстракции;
- утечки деталей backend;
- инверсия зависимостей без тяжёлой объектной модели.

Основная практика — рассматривать разные варианты границ и объяснять последствия
каждого, а не сразу реализовывать наиболее универсальный интерфейс.

### Критерий завершения

Можно обосновать, почему низкоуровневый слой не должен знать о материалах и
объектах сцены, а типы конкретного API не должны покидать его backend.

## 6. Формирование кадра

### Цель

Перейти от мышления отдельными draw calls к мышлению полным кадром.

### Область изучения

- immediate submission;
- накопление render commands;
- render lists;
- сортировка;
- state changes;
- batching;
- instancing;
- opaque и transparent geometry;
- порядок отрисовки;
- render queues;
- passes;
- зависимости между passes;
- промежуточные render targets;
- frame graph как более развитая модель;
- frame-local memory;
- double и triple buffering.

Нужно понимать конфликт требований:

```text
корректный порядок
<-> минимум переключений состояния
<-> параллельная подготовка
<-> предсказуемое потребление памяти
```

### Критерий завершения

Можно спроектировать последовательность построения кадра и объяснить, почему
объекты нельзя всегда сортировать только по материалу или только по расстоянию.

## 7. Материалы и шейдерная система

### Цель

Понять связь между данными игры и программами, выполняемыми GPU.

### Область изучения

- shader stages;
- shader inputs и outputs;
- uniforms и constants;
- uniform и constant buffers;
- textures и samplers;
- material parameters;
- reflection;
- shader variants;
- pipeline state;
- binding layouts;
- частота обновления данных;
- per-frame, per-material и per-object данные;
- hot reload;
- компиляция и диагностика шейдеров.

Особенно важно разделять:

```text
Pipeline     — способ рисования
Material     — параметры поверхности
RenderObject — параметры экземпляра
```

### Критерий завершения

Для конкретного параметра можно определить его уровень, владельца и частоту
передачи на GPU.

## 8. Масштабирование сцены

### Цель

Понять, почему архитектура небольшого примера перестаёт работать на большой
локации.

### Область изучения

- spatial organization;
- frustum culling;
- occlusion;
- LOD;
- instancing;
- terrain organization;
- chunking;
- streaming;
- resource budgets;
- texture atlases и arrays;
- mipmapping;
- управление видимостью;
- CPU и GPU bottlenecks;
- профилирование;
- количество draw calls;
- bandwidth;
- overdraw.

Архитектурные решения принимаются по измерениям, а не по предположению, что
определённый подход должен быть быстрее.

### Критерий завершения

Можно определить потенциальное узкое место, выбрать способ измерения и
интерпретировать результат.

## 9. Освещение и построение изображения

### Цель

Получить системное понимание визуальной стороны рендера.

### Область изучения

- модели отражения;
- источники света;
- forward rendering;
- deferred rendering;
- shadow mapping;
- environment lighting;
- baked lighting;
- fog;
- transparency;
- alpha testing;
- HDR;
- tone mapping;
- gamma и color spaces;
- post-processing.

До выбора техники нужно понимать:

- сколько раз обрабатывается геометрия;
- какие промежуточные изображения нужны;
- как решение масштабируется.

### Критерий завершения

Можно сравнить несколько техник по качеству, сложности, памяти и
производительности.

## 11. Explicit graphics API и DirectX 12

### Цель

Сделать ранее скрытые обязанности приложения явными.

К этому этапу следует переходить после уверенного понимания предыдущих уровней.

### Область изучения

- device и adapters;
- command queues;
- command allocators;
- command lists;
- descriptor heaps;
- root signatures;
- pipeline state objects;
- resource states;
- barriers;
- upload и default heaps;
- fences;
- frame resources;
- CPU/GPU synchronization;
- validation layer;
- устройство swap chain;
- обработка device loss.

Подход к изучению:

```text
понять общее графическое понятие
→ найти его представление в OpenGL
→ изучить его явное представление в DirectX 12
→ сравнить ответственность приложения
```

### Критерий завершения

Код DirectX 12 воспринимается не как церемония, а как явное управление
ресурсами, состояниями, командами и синхронизацией.

## 12. Собственная архитектура Clearwater

### Цель

Сформировать архитектуру движка на основе понятых требований и накопленного
опыта.

Процесс принятия каждого решения:

1. Определить реальные требования.
2. Зафиксировать ограничения.
3. Рассмотреть несколько вариантов.
4. Выбрать самый простой достаточный вариант.
5. Явно описать ownership.
6. Определить направление зависимостей.
7. Проверить решение другим или null backend.
8. Измерить поведение.
9. Удалить преждевременную универсальность.

Текущий AI-рефакторинг следует использовать как объект архитектурного разбора:

- какую проблему решает каждый слой;
- существует ли эта проблема сейчас;
- какие альтернативы возможны;
- где решение преждевременно;
- что может помешать DirectX 12;
- какие lifetime-инварианты отсутствуют;
- какие решения можно упростить.

Он является материалом для анализа, а не готовым ответом.

## Постоянная практика

На протяжении обучения чередуются четыре типа работы.

### Исследование

Небольшие изолированные эксперименты для проверки одной гипотезы.

### Реконструкция

Восстановление изученной системы по памяти без копирования.

### Анализ

Трассировка данных, ownership и control flow в Clearwater или другом движке.

### Проектирование

Несколько вариантов интерфейса с письменным сравнением компромиссов до начала
реализации.

Рекомендуемая пропорция:

```text
40% — самостоятельная практика
25% — теория
20% — чтение и анализ чужого кода
15% — письменное объяснение и повторение
```

## Использование ИИ

ИИ используется как:

- преподаватель;
- собеседник;
- ревьюер;
- генератор вопросов;
- помощник в диагностике;
- оппонент архитектурного решения.

ИИ не должен быть автором учебной реализации.

Пример рабочего запроса:

> Объясни модель, но не проектируй за меня. Затем задай вопросы, предложи
> проблему для исследования и проверь моё объяснение. Код показывай только после
> моей попытки.

При затруднении сначала нужно:

1. Описать ожидаемое поведение.
2. Описать фактическое поведение.
3. Назвать собственные гипотезы.
4. Собрать наблюдения.
5. Только затем просить подсказку.

## Измерение прогресса

Тема освоена, если получается:

- объяснить её без терминологической дымки;
- предсказать поведение до запуска;
- воспроизвести ключевую часть без образца;
- диагностировать поломку;
- сравнить альтернативы;
- определить ownership;
- перенести понятие между OpenGL и DirectX 12;
- понять чужое решение и аргументированно с ним не согласиться.

«Я узнаю этот код» — ещё не понимание.

«Я могу объяснить, изменить, сломать, диагностировать и спроектировать иначе» —
понимание.

## Общая траектория

```text
GPU и кадр
→ графический API
→ ресурсы и lifetime
→ сущности рендерера
→ слои
→ формирование кадра
→ материалы и шейдеры
→ масштабирование сцены
→ освещение
→ asset pipeline
→ DirectX 12
→ осознанная архитектура Clearwater
```

Это не линейный курс, который можно однажды окончательно закончить. Один и тот
же круг будет повторяться несколько раз на новом уровне глубины.
